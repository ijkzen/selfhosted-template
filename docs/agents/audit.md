# 代码质量审计

模块级代码审查与整改的流程规范。适用于「全仓过一遍、把问题变成可排期的清单」这类任务。方法来自 llm-gateway 的一次全仓审计（21 个模块票 + 22 份 FINDINGS），与 `wayfinder`、`code-review`、`diagnosing-bugs` 三个 skill 衔接使用。

## 核心纪律

**审改分离**：审查阶段只产出清单，不改代码。改动在地图走完后统一排期实施。理由——审和改混在一起时，改动会掩盖尚未审出的问题，且中断后无法判断进度。

**行号必须逐条复核**：子代理（或任何自动化）给出的报告是起点，不是结论。每条 FINDINGS 在写入清单前，主代理要对着磁盘逐行核对行号与行为描述；复核后再标注哪些是真问题、哪些部分成立、哪些不成立。

**每条发现带证据**：编号 / 严重度 / 维度 / 一句话 / 文件与行号。没有行号锚点的条目不算发现。

## 严重度定义

| 级别 | 含义 |
|------|------|
| P1 | 高：正确性缺陷、数据损坏、用户可见故障、吞吐瓶颈 |
| P2 | 中：特定条件下的错误行为、可观测性缺失、明显重复 |
| P3 | 低：一致性/注释漂移、微性能、测试缺口、简洁性收敛 |

## 目录约定

```
.scratch/<effort>-<YYYY-MM-DD>/
├── map.md          # 地图：Destination / Notes / Decisions so far / 实施进度
├── MODULES.md      # 模块边界盘点产物（审查范围的唯一权威）
├── issues/NN-<slug>.md    # 每个模块一张审查票（Question → Answer）
└── findings/NN-<slug>.md  # 每票一份 FINDINGS（汇总表 + 各条证据）
```

## 流程

1. **模块边界盘点（阻塞票）**：先把全仓切成模块——列出每个模块的文件归属、对外接口、依赖方向，并显式处理「寄居文件」（逻辑上属于别的模块却放在此处）与「散落候选」（同一件事在多处实现）。产物是 `MODULES.md`，它是后续所有票审查范围的唯一权威，切分有争议时先改它再开票。
2. **分票**：一个模块一张票，票内写清审查范围（文件清单）、依赖的其它模块接口、该模块已登记的历史遗留项。
3. **四轴审查**：每票按四个轴通读——逻辑正确性 / 实现简洁 / 测试覆盖 / 模块间调用，外加一轮专门的性能与内存审查。
4. **产出 FINDINGS**：汇总表（编号+严重度+维度+一句话）在前，各条证据在后。已修复的条目在汇总表里就地标注状态与日期，不另建文件。
5. **拍板**：需要产品/设计取舍的（bug 还是设计如此、重构范围、要不要删）当场问用户并记录结论；有明确唯一解的直接进清单。
6. **归位**：不属于本模块的历史遗留项，转到对应模块票的 Question 里显式列出，不要就地消化。
7. **统一排期实施**：按 P1 → P2 → P3 分批，每批走完整质量门（见 `AGENTS.md` 的提交前置动作）并独立提交。实施结论回写到对应 findings 文件的「实施进度」段。

## FINDINGS 条目模板

```markdown
### NN-MM 一句话标题（P2，维度）【已修复 YYYY-MM-DD】

现象：当前代码在什么条件下会怎样（用户可见后果优先）。

证据：`src/foo.rs:120-134` 的分支只落库不写日志；对照 `src/foo.rs:196-207` 的降级分支带 warn。

建议：改法一句话；有多个方案时列出取舍与推荐。
```

## 与 skill 的配合

- `wayfinder`：把「审完整个仓库」拆成决策票并跟踪，地图即 `map.md`。
- `grilling` / `AskUserQuestion`：条目需要用户拍板时用，结论写进票的 Answer。
- `code-review`：审查单个 diff/PR 时用它；本流程面向「没有明确 diff 的存量代码」。
- `diagnosing-bugs`：审查中发现可复现的 bug 时，用它走诊断循环。
